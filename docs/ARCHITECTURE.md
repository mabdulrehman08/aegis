# Prototype architecture and safety decisions

## Boundaries

`optimization/` is a pure request/result boundary: typed synthetic scene, explicit
requirements, active work, associated observations, revisions, and clock go in;
new assignment recommendations, preserved work, route geometry, reasons, and
measured diagnostics come out. There is no dispatch or transport in the solver.

`backend/app/simulation/` is the authoritative local incident coordinator. Its
locked in-memory state is process-local, non-durable, and not production-secure.
Request-local optimization must run outside the state lock and be committed only
if its revision assumptions remain valid. API operations use worker threads;
WebSockets deliver snapshots/events and never perform solver or dispatch actions.
Do not run multiple Uvicorn workers for this prototype.

`backend/app/services/advisory.py` explains structured facts. Optional LLM output
is limited to selecting known fact IDs; omitted facts are restored and arbitrary
text/state is not accepted. Solver and state gates do not depend on the provider.

CV, hardware, and frontend applications remain owned by their teammates. Backend
observations are not casualty records until an explicit association is made.
Medical assessments are human-entered simulation data, never generated by CV.

## State and authorization

The existing production contract remains reserved. Additive simulation endpoints
are documented separately for review, under `/api/v1/simulations/`; they are not
implementations of reserved real dispatch endpoints. A local `operator_id` records
the claimed simulation actor, **not authenticated identity**. No medical or
production authorization can be inferred from this local prototype.

Recommendations are advisory. Approval must name the exact current proposal;
scene changes or expiry invalidate execution assumptions. A dispatch consumes
one valid approval atomically, reserves responders, and creates local command IDs.
Only correlated simulation device events can advance that local assignment.
Acknowledgement is not approval; completion is not evidence of clinical success.

Approved work is never silently reassigned by the solver. Existing assignments
are returned separately from new work, so they cannot be redispatched accidentally.
After a map change, preserve historical route evidence and flag the need for
operator review rather than silently replacing a previously approved path.

## Uncertainty and replanning

Observations retain their own IDs, stable track IDs, update/last-seen timestamps,
confidence, and visibility state. Associated stale, lost, occluded, low-confidence,
future-dated, or position-mismatched observations conservatively exclude new work.
Absent observation data is not a fabricated clinical conclusion. A human-known
synthetic scene can still be planned without a live camera.

Replanning is revision-driven and bounded, never an unbounded solver loop. New
recommendations still need fresh approval. The frontend must display unassigned
reasons, unknown assessments, stale inputs, and historical active-route warnings.

## Deliberate limits

- Four-neighbor A* is conservative, not a continuous physical motion controller.
- The integer travel objective rounds world-meter path lengths to millimeters;
  returned distances remain actual polyline lengths, not ETAs.
- Synthetic benchmarks measure matching, travel, runtime, and violations only.
- No real device transport, clinical validation, cloud deployment, dataset
  training, or PPO policy exists. A future real system needs a separate reviewed
  design for identity, persistence, auditing, delivery guarantees, and safety.
